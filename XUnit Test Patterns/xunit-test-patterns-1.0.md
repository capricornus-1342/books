# xUnit Test Patterns — краткий справочник (BP 1.0)

> **Gerard Meszaros. xUnit Test Patterns: Refactoring Test Code.**
> Addison-Wesley, 2007. — 944 с.

Книга состоит из **4 частей**, **27 глав** и **7 приложений**. В каталоге —
**68 базовых паттернов**; с учётом алиасов и вариаций (приложение G) — около
**288 имён** (68 паттернов + 67 алиасов + 153 вариации). Отдельно книга
описывает **18 «запахов» тестов** (test smells): **15 конкретных запахов**
в трёх категориях плюс **3 названия самих категорий** — ровно 18 позиций
каталога.

**Термины.** *SUT (System Under Test)* — тестируемая система или компонент.
*Фикстура (fixture)* — исходное состояние и окружение, необходимое тесту:
объекты, данные, подключения, файлы. *Тестовый дублёр (test double)* — объект,
заменяющий реальную зависимость SUT в тесте.

## 2. Каталог паттернов

Формат записи: **Русское название (English name)** — зачем нужен.
Названия даны на русском, оригиналы — в скобках для сверки с книгой.

### Глава 18. Test Strategy Patterns — паттерны стратегии тестирования (15)

#### Стратегии (10)

1. **Фреймворк автоматизации тестирования (Test Automation Framework)** —
   набор библиотек и соглашений, который берёт на себя запуск тестов,
   отчётность и жизненный цикл; тестировщик пишет только специфичную для
   теста логику.
2. **Сценарный тест (Scripted Test)** — тест автоматизируется вручную, кодом;
   даёт полный контроль, но требует навыков и поддержки.
3. **Записанный тест (Recorded Test)** — действия пользователя записываются
   инструментом и воспроизводятся; быстрый старт, но хрупкость при изменении UI.
4. **Тест, управляемый данными (Data-Driven Test)** — логика теста отделена
   от данных; один сценарий прогоняется по набору входов и ожиданий из файла.
5. **Манипуляция через «чёрный ход» (Back Door Manipulation)** — подготовка
   или проверка состояния в обход публичного API (например, напрямую в БД),
   чтобы не тащить в тест лишние зависимости.
6. **Тест слоя (Layer Test)** — тестирование отдельного слоя архитектуры
   (UI, сервис, persistence) с изоляцией от остальных слоёв.
7. **Свежая фикстура (Fresh Fixture)** — каждый тест создаёт собственный новый
   набор данных и объектов; даёт независимость и повторяемость.
8. **Разделяемая фикстура (Shared Fixture)** — один экземпляр фикстуры
   переиспользуется несколькими тестами ради скорости, ценой связанности.
9. **Стандартная фикстура (Standard Fixture)** — для нескольких тестов
   используется одна и та же схема (дизайн) фикстуры; упрощает понимание.
10. **Минимальная фикстура (Minimal Fixture)** — в тесте создаётся только то,
    что действительно нужно; меньше сложности и хрупкости.

#### Паттерны разделяемой фикстуры (Shared Fixture Patterns, 5)

11. **Сцепленные тесты (Chained Tests)** — тест опирается на состояние,
    оставленное предыдущим тестом; быстрее, но нарушает независимость.
12. **Ленивая установка (Lazy Setup)** — дорогая фикстура создаётся при первом
    обращении, а не заранее; экономит время, если тест может её не использовать.
13. **Предварительно построенная фикстура (Prebuilt Fixture)** — общая фикстура
    готовится отдельно (скриптом или перед запуском), тесты только используют её.
14. **Декоратор установки (Setup Decorator)** — тестовый набор оборачивается
    декоратором, который поднимает общую фикстуру до тестов и убирает после.
15. **Установка фикстуры набора (SuiteFixture Setup)** — специальные методы
    фреймворка создают и разрушают общую фикстуру один раз на весь набор тестов.

### Глава 19. xUnit Basics Patterns — базовые паттерны xUnit (11)

1. **Сообщение утверждения (Assertion Message)** — в проверку добавляется текст,
   объясняющий, что именно ожидалось и что пошло не так.
2. **Метод утверждения (Assertion Method)** — проверка выносится в
   переиспользуемый метод, который сравнивает факт с ожиданием и падает
   с понятным сообщением.
3. **Четырёхфазный тест (Four-Phase Test)** — каждый тест состоит из setup,
   exercise, verify и teardown; делает тест предсказуемым и читаемым.
4. **Обнаружение тестов (Test Discovery)** — фреймворк сам находит тесты в коде
   (по именам или атрибутам), избавляя от ручной регистрации.
5. **Перечисление тестов (Test Enumeration)** — тесты регистрируются и
   перечисляются вручную; даёт контроль, но требует поддержки.
6. **Тестовый метод (Test Method)** — один тест = один метод с понятным именем;
   базовый строительный блок xUnit.
7. **Запускатель тестов (Test Runner)** — приложение или инструмент, который
   находит, запускает тесты и показывает результаты.
8. **Выбор тестов (Test Selection)** — фреймворк решает, какие тесты запускать
   в данном прогоне (по атрибутам или категориям).
9. **Объект набора тестов (Test Suite Object)** — коллекция тестов, реализующая
   стандартный интерфейс, чтобы запускать их как группу.
10. **Класс тест-кейса (Testcase Class)** — класс, группирующий связанные
    тестовые методы и общую для них фикстуру.
11. **Объект тест-кейса (Testcase Object)** — каждый тест представлен
    объектом-командой, который можно передать раннеру и выполнить.

### Глава 20. Fixture Setup Patterns — паттерны установки фикстуры (4)

1. **Метод создания (Creation Method)** — создание объекта прячется за методом
   с говорящим именем, чтобы тест читался как сценарий.
2. **Делегированная установка (Delegated Setup)** — тест создаёт свою фикстуру,
   вызывая методы создания, а не дублируя код.
3. **Неявная установка (Implicit Setup)** — общая фикстура строится в `setUp`,
   который фреймворк вызывает перед каждым тестом.
4. **Встроенная установка (Inline Setup)** — каждый тест сам создаёт нужную
   фикстуру прямо в своём теле; максимально явно.

### Глава 21. Result Verification Patterns — паттерны проверки результатов (7)

1. **Проверка поведения (Behavior Verification)** — фиксируются косвенные
   выходы SUT (вызовы зависимостей) и сравниваются с ожидаемым поведением.
2. **Пользовательское утверждение (Custom Assertion)** — создаётся утверждение
   под конкретную предметную область, сравнивающее только важные атрибуты.
3. **Дельта-утверждение (Delta Assertion)** — проверяется не абсолютное
   состояние, а разница между состоянием до и после действия.
4. **Защитное утверждение (Guard Assertion)** — вместо `if` в тесте ставится
   утверждение, которое сразу падает при нарушении предусловия.
5. **Параметризованный тест (Parameterized Test)** — один тестовый сценарий
   выполняется для набора параметров, уменьшая дублирование.
6. **Проверка состояния (State Verification)** — после действия инспектируется
   состояние SUT и сравнивается с ожидаемым.
7. **Утверждение незавершённого теста (Unfinished Test Assertion)** — в
   недописанный тест ставится заведомо падающее утверждение, чтобы он не
   «зеленел» случайно.

### Глава 22. Fixture Teardown Patterns — паттерны демонтажа фикстуры (4)

1. **Автоматический демонтаж (Automated Teardown)** — тест регистрирует
   созданные ресурсы, а фреймворк автоматически освобождает их после теста.
2. **Демонтаж сборщиком мусора (Garbage-Collected Teardown)** — очистка
   отдаётся сборщику мусора, когда язык и среда это позволяют.
3. **Неявный демонтаж (Implicit Teardown)** — очистка выносится в `tearDown`,
   который фреймворк вызывает после каждого теста.
4. **Встроенный демонтаж (Inline Teardown)** — очистка пишется в конце
   тестового метода сразу после проверок.

### Глава 23. Test Double Patterns — паттерны тестовых дублёров (8)

1. **Настраиваемый тестовый дублёр (Configurable Test Double)** — один дублёр
   можно настроить на разные возвраты и ожидания в разных тестах.
2. **Фейковый объект (Fake Object)** — зависимость заменяется упрощённой
   рабочей реализацией (например, in-memory БД).
3. **Жёстко закодированный тестовый дублёр (Hard-Coded Test Double)** —
   возвраты и ожидания прописаны в коде дублёра под конкретный тест.
4. **Мок-объект (Mock Object)** — дублёр проверяет, что SUT правильно
   взаимодействует с зависимостью (ожидаемые вызовы).
5. **Тестовый дублёр (Test Double)** — общий термин для любого объекта,
   заменяющего реальную зависимость в тесте.
6. **Тестовый шпион (Test Spy)** — дублёр записывает вызовы к нему, чтобы
   потом проверить их в тесте.
7. **Тестовая заглушка (Test Stub)** — дублёр возвращает заранее заданные
   значения, чтобы управлять входами SUT.
8. **Подкласс, специфичный для теста (Test-Specific Subclass)** — в подклассе
   SUT добавляются методы или поведение, нужные только тесту.

### Глава 24. Test Organization Patterns — паттерны организации тестов (7)

1. **Именованный набор тестов (Named Test Suite)** — группа тестов получает имя
   и может запускаться отдельно.
2. **Тестовый помощник (Test Helper)** — класс-помощник хранит переиспользуемые
   вспомогательные методы тестов.
3. **Вспомогательный метод теста (Test Utility Method)** — повторяющаяся
   тестовая логика прячется за методом с понятным именем.
4. **Класс тест-кейсов на класс (Testcase Class per Class)** — все тесты одного
   класса SUT собраны в одном тест-классе.
5. **Класс тест-кейсов на функциональность (Testcase Class per Feature)** —
   тесты группируются по тестируемой возможности, а не по классу.
6. **Класс тест-кейсов на фикстуру (Testcase Class per Fixture)** — тесты
   с одинаковой фикстурой собраны вместе.
7. **Суперкласс тест-кейсов (Testcase Superclass)** — общая тестовая логика
   выносится в абстрактный суперкласс, наследуемый тест-классами.

### Глава 25. Database Patterns — паттерны для баз данных (4)

1. **Песочница базы данных (Database Sandbox)** — у каждого разработчика или
   тестировщика своя изолированная БД, чтобы тесты не мешали друг другу.
2. **Тест хранимой процедуры (Stored Procedure Test)** — для каждой хранимой
   процедуры пишется полностью автоматизированный тест.
3. **Демонтаж усечением таблиц (Table Truncation Teardown)** — после теста
   таблицы, которые он менял, очищаются через `TRUNCATE`.
4. **Демонтаж откатом транзакции (Transaction Rollback Teardown)** — изменения
   теста откатываются `rollback` незакоммиченной транзакции.

### Глава 26. Design-for-Testability Patterns — паттерны проектирования для тестируемости (4)

1. **Внедрение зависимостей (Dependency Injection)** — зависимость передаётся
   в SUT извне (конструктор, параметр, setter), что позволяет подставить дублёра.
2. **Поиск зависимостей (Dependency Lookup)** — SUT сам запрашивает зависимость
   у реестра, фабрики или локатора; связывание гибче, но тестировать сложнее.
3. **Скромный объект (Humble Object)** — сложная логика выносится из
   «неудобного» для тестов окружения (UI, БД) в отдельный тестируемый объект.
4. **Тестовый хук (Test Hook)** — в SUT добавляется точка, позволяющая тесту
   изменить поведение или состояние.

### Глава 27. Value Patterns — паттерны значений (4)

1. **Производное значение (Derived Value)** — значения вычисляются из других
   значений, чтобы не дублировать константы и снизить хрупкость.
2. **Фиктивный объект (Dummy Object)** — передаётся объект-пустышка, который
   нужен только для заполнения параметра и не используется.
3. **Сгенерированное значение (Generated Value)** — подходящее значение
   генерируется при каждом запуске (например, уникальный ID).
4. **Литеральное значение (Literal Value)** — в тесте используются явные
   константы, чтобы ожидания были наглядными.

## 3. Каталог запахов тестов

**Запах (smell)** — это внешний признак проблемы, а не сама проблема. Запах
говорит, *что* не так с тестом или проектом; конкретную причину и лечение
надо искать по паттернам. Книга делит запахи на три категории: **код**
(видно при чтении теста), **поведение** (видно при запуске) и **проект**
(видно на уровне команды и процесса).

| Категория | Когда заметен | Конкретных запахов |
|---|---|---:|
| Code Smells — запахи кода | при чтении тестового кода | 5 |
| Behavior Smells — запахи поведения | при запуске тестов | 6 |
| Project Smells — запахи проекта | на уровне проекта и процесса | 4 |
| **Итого** | | **15** |

### Глава 15. Code Smells — запахи кода (5)

1. **Непонятный тест (Obscure Test)** — тест трудно понять с первого взгляда:
   он слишком длинный, перегружен деталями, использует загадочные данные или
   проверяет не то, что обещает имя. Читатель не может быстро ответить, что
   тестируется и почему ожидается именно такой результат. Помогают:
   осмысленные имена, минимальная фикстура (`Minimal Fixture`), методы
   создания (`Creation Method`), вспомогательные методы (`Test Utility Method`)
   и пользовательские утверждения (`Custom Assertion`).
2. **Условная логика в тесте (Conditional Test Logic)** — в тесте есть `if`,
   циклы, `switch` или `try/catch`. Один метод проверяет сразу несколько
   сценариев, часть кода может вообще не выполниться, а падение трудно
   локализовать. Помогают: `Parameterized Test`, разбиение на несколько
   простых тестов, `Guard Assertion`, вынос логики в `Test Utility Method`.
3. **Код, который трудно тестировать (Hard-to-Test Code)** — сам SUT неудобно
   тестировать: зависимости создаются внутри (`new`, статические вызовы),
   классы сильно связаны, есть асинхронность или скрытые побочные эффекты.
   Помогают паттерны проектирования для тестируемости: `Dependency Injection`,
   `Dependency Lookup`, `Humble Object`, `Test Hook`, а также `Layer Test`
   и `Test Double`.
4. **Дублирование тестового кода (Test Code Duplication)** — код создания
   фикстуры и проверок копируется из теста в тест. Любая правка требует
   менять много мест, а копии постепенно расходятся. Помогают:
   `Creation Method`, `Test Utility Method`, `Test Helper`,
   `Testcase Superclass`, `Parameterized Test`.
5. **Тестовая логика в продакшн-коде (Test Logic in Production)** — в боевом
   коде остаются ветки, методы или поля «только для тестов». Продакшн ведёт
   себя не так, как тестировался, и появляется риск, что тестовая ветка
   сработает у пользователя. Помогают: `Test Hook` в минимальном объёме,
   DfT-паттерны и вынос тестовой логики обратно в тест.

### Глава 16. Behavior Smells — запахи поведения (6)

6. **Рулетка утверждений (Assertion Roulette)** — в одном тесте несколько
   утверждений без пояснений, и при падении невозможно понять, какое именно
   сработало. Помогают: `Assertion Message`, правило «один тест — одна
   причина падения», `Custom Assertion`.
7. **Нестабильный тест (Erratic Test)** — тест то проходит, то падает без
   изменений в коде. Причины: зависимость от порядка тестов (`Interacting
   Tests`), от общего состояния (`Lonely Test`), от времени или случайности
   (`Nondeterministic Test`), утечки ресурсов, параллельный запуск
   (`Test Run War`). Помогают: `Fresh Fixture`, `Automated Teardown`,
   изоляция тестов, детерминированные значения (`Generated Value`,
   `Derived Value`).
8. **Хрупкий тест (Fragile Test)** — тест ломается при изменениях, которые
   не затрагивают проверяемое поведение. Чувствительность бывает к интерфейсу
   (`Interface Sensitivity`), поведению (`Behavior Sensitivity`), данным
   (`Data Sensitivity`), контексту (`Context Sensitivity`), точному равенству
   (`Sensitive Equality`), фикстуре (`Fragile Fixture`); также выделяют
   `Overcoupled Test` и `Overspecified Software`. Помогают:
   `Minimal Fixture`, `Custom Assertion`, `Delta Assertion`, `Test Double`,
   `Back Door Manipulation`, проверка через стабильный интерфейс.
9. **Частая отладка (Frequent Debugging)** — почти каждое падение требует
   ручной отладки: тест не сообщает, что и где сломалось. Помогают:
   `Assertion Message`, `Custom Assertion`, говорящие имена тестов,
   `Four-Phase Test`, одна проверка на тест.
10. **Ручное вмешательство (Manual Intervention)** — при каждом запуске нужен
    человек: ввести данные, подготовить окружение, глазами проверить
    результат (`Manual Fixture Setup`, `Manual Event Injection`,
    `Manual Result Verification`). Помогают: автоматические setup/verify/
    teardown, `Back Door Manipulation`, `Fake Object`, `Test Runner`.
11. **Медленные тесты (Slow Tests)** — прогон занимает слишком много времени,
    поэтому тесты запускают редко. Причины: реальные БД, сеть и UI, тяжёлые
    компоненты, слишком много сквозных тестов. Помогают: `Test Double`,
    `Shared Fixture`, `Database Sandbox`, `Layer Test`, разумное разделение
    unit- и integration-тестов.

### Глава 17. Project Smells — запахи проекта (4)

12. **Багованные тесты (Buggy Tests)** — ошибки содержатся в самих тестах:
    они падают на рабочем коде или, наоборот, пропускают дефекты. Причины:
    сложные и дублирующиеся тесты, слабые проверки, отсутствие ревью.
    Помогают: рефакторинг тестов, `Custom Assertion`, ревью тестового кода,
    мутационное тестирование.
13. **Разработчики не пишут тесты (Developers Not Writing Tests)** — команда
    почти не пишет автоматические тесты. Причины: нехватка времени, неверная
    стратегия автоматизации, отсутствие навыков и инфраструктуры. Помогают:
    `Test Automation Framework`, TDD, обучение и снижение порога входа.
14. **Высокая стоимость поддержки тестов (High Test Maintenance Cost)** —
    поддержка тестов съедает слишком много времени: после каждого
    рефакторинга SUT приходится править десятки тестов. Причины: хрупкость,
    дублирование, плохая организация. Помогают: устранение `Fragile Test`
    и `Test Code Duplication`, `Testcase Class per Fixture`/`per Feature`,
    `Test Helper`, рефакторинги тестов.
15. **Баг в продакшене (Production Bugs)** — дефекты находят на формальном
    тестировании или уже у пользователей, хотя тесты есть. Причины: непокрытые
    требования и код (`Untested Requirement`, `Untested Code`), тесты, которые
    никогда не падают (`Neverfail Test`), потерянные и редко запускаемые тесты
    (`Lost Test`, `Infrequently Run Tests`). Помогают: покрытие требований,
    `Test Selection`, CI, мутационное тестирование, анализ пробелов.

### Три категории — оставшиеся 3 позиции каталога

Именно поэтому в аннотации книги говорится про **18 запахов**: к 15 конкретным
запахам добавляются три названия категорий.

16. **Запахи кода (Code Smells)** — проблемы, которые видны при чтении
    тестового кода.
17. **Запахи поведения (Behavior Smells)** — проблемы, которые проявляются
    при запуске тестов.
18. **Запахи проекта (Project Smells)** — проблемы, которые заметны на уровне
    проекта: скорость, стоимость, доверие к тестам.

## 5. Как пользоваться справочником

1. **Изучение.** Читайте часть I целиком: она объясняет цели, принципы
   и стратегии, без которых паттерны превращаются в набор рецептов.
2. **Диагностика.** Если тесты стали медленными, хрупкими или непонятными,
   начните с части II (запахи) — она помогает найти корневую причину.
3. **Решение.** По запаху или задаче выбирайте паттерн из части III:
   описание каждого паттерна отвечает на вопросы «зачем», «когда применять»
   и «какие есть альтернативы».
4. **Сверка терминов.** Для разных xUnit-фреймворков используйте приложения B и C:
   одни и те же понятия там называются по-разному.
5. **Рефакторинг.** Приложения A и G помогают перейти от «плохого» теста
   к «хорошему», не меняя его смысл.
