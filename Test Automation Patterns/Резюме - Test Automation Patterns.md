# Паттерны тестовой автоматизации — краткое резюме

**Книга:** «Паттерны проектирования автоматизированного тестирования» (Test Automation Patterns / «A Journey Through Test Automation Patterns»)
**Авторы:** Дороти Грэм, Серапион Эдвард (Dorothy Graham, Seretta Gamba)

Паттерн — проверенное на практике решение типичной проблемы автоматизации. Это не готовая инструкция, а идея, которую адаптируешь под свой проект. Паттерны делятся на 4 категории + анти-паттерны (failure patterns).

---

## 1. Процессные паттерны (Process Patterns)
*Как выстроить и улучшить сам процесс автоматизации.*

| Паттерн | Зачем нужен |
|---|---|
| ASK FOR HELP — Проси о помощи | Не тратить время впустую, пытаясь всё сделать самому |
| AUTOMATE WHAT'S NEEDED — Автоматизируй нужное | Автоматизировать то, что реально нужно разработчикам/тестерам, даже если это не тесты |
| CELEBRATE SUCCESS — Празднуй успех | Мотивация команды на важных вехах проекта |
| CHECK-TO-LEARN — Проверяй, чтобы учиться | Новичкам быстрее освоиться, проверяя здоровье существующего тест-кода |
| DOCUMENT THE TESTWARE — Документируй тестовый код | Скрипты и данные должны быть понятны другим и через время |
| FULL TIME JOB — Полная занятость | Команда автоматизации должна работать на полную ставку |
| GOOD DEVELOPMENT PROCESS — Хороший процесс разработки | К тестовому коду применять те же практики, что и к продакшену |
| GOOD PROGRAMMING PRACTICES — Хорошие практики программирования | Тесты пишутся как качественное ПО, а не «как получится» |
| KILL THE ZOMBIES — Убей зомби | Удалять/архивировать неиспользуемые тесты и данные, чтобы не путали |
| LAZY AUTOMATOR — Ленивый автоматизатор | Лень двигает к переиспользованию и простым решениям |
| LEARN FROM MISTAKES — Учись на ошибках | Ошибки — источник улучшений в следующих итерациях |
| LOOK AHEAD — Смотреть вперёд | Следить за новыми инструментами, методами и паттернами сообщества |
| LOOK FOR TROUBLE — Ищи проблемы заранее | Решать потенциальные проблемы, пока они не стали неуправляемыми |
| MAINTAIN THE TESTWARE — Поддерживай тестовый код | Обслуживать скрипты и данные с самого начала, иначе всё протухнет |
| PAIR UP — Парное тестирование | Новички учатся у опытных через совместную работу |
| REFACTOR THE TESTWARE — Рефакторинг тестов | Регулярно перестраивать тестовый код, чтобы он не устаревал |
| SET STANDARDS — Установи стандарты | Единые правила оформления артефактов автоматизации |
| SHARE INFORMATION — Делись информацией | Обмен с менеджерами, разработчиками и тестерами снижает риски |
| SHORT ITERATIONS — Короткие итерации | Быстрая обратная связь и адаптация автоматизации |
| TAKE SMALL STEPS — Делай маленькие шаги | Искать маленькие приносящие ценность приращения |
| TEST THE TESTS — Тестируй тесты | Проверять скрипты так же, как и продакшен-код |
| WHOLE TEAM APPROACH — Вся команда вместе | Тестеры, кодеры и другие роли работают в одной команде |

## 2. Управленческие паттерны (Management Patterns)
*Как управлять проектом автоматизации.*

| Паттерн | Зачем нужен |
|---|---|
| AUTOMATE EARLY — Автоматизируй рано | Чем раньше запустишь тесты, тем раньше увидишь результаты |
| AUTOMATION ROLES — Роли в автоматизации | В команде нужны разные навыки и чёткое распределение ролей |
| DEDICATED RESOURCES — Выделенные ресурсы | Полная занятость команды + нужные инструменты и машины |
| DEPUTY — Заместитель | Дублировать ключевых экспертов, чтобы не зависеть от одного человека |
| DO A PILOT — Сделай пилот | На пилотном проекте понять, как лучше автоматизировать приложение |
| GET ON THE CLOUD — В облако | Виртуальные машины вместо локальных — гибкость и масштабируемость |
| GET TRAINING — Обучение | Планировать обучение всех участников проекта |
| KNOW WHEN TO STOP — Знай, когда остановиться | Не все (и не всегда) тесты стоит автоматизировать |
| MANAGEMENT SUPPORT — Поддержка менеджмента | Без поддержки руководства проект не выживет: продавай идею и отчитывайся |
| MIX APPROACHES — Мешай подходы | Не бояться использовать разные инструменты и подходы |
| PLAN SUPPORT ACTIVITIES — Планируй поддержку | Время на поддержку и сопутствующие задачи — часть плана |
| PREFER FAMILIAR SOLUTIONS — Привычные решения | При равных преимуществах — инструмент, уже знакомый в компании |
| RIGHT TOOLS — Правильные инструменты | Выбор под приложение, окружение, людей, бюджет и уровень тестирования |
| SELL THE BENEFITS — Продавай выгоду | Сообщать руководству о достижимых и достигнутых benefits |
| SET CLEAR GOALS — Чёткие цели | Определить цели проекта с самого начала |
| SIDE-BY-SIDE — Сравнение инструментов | Выбирать инструмент, пробуя их бок о бок |
| TESTABLE SOFTWARE — Тестируемое ПО | Заранее найти в SUT то, что делает автоматизацию невозможной |
| TEST AUTOMATION BUSINESS CASE — Бизнес-кейс | Обосновать автоматизацию как обычный проект + её специфика |
| TEST AUTOMATION OWNER — Владелец автоматизации | Назначить ответственного за всё усилие по автоматизации |

## 3. Паттерны проектирования (Design Patterns)
*Как спроектировать тестовый код, чтобы он был эффективным и легко поддерживаемым.*

| Паттерн | Зачем нужен |
|---|---|
| ABSTRACTION LEVELS — Уровни абстракции | Тест-код с слоями абстракции: изменения не ломают всё |
| AUTOMATE GOOD TESTS — Автоматизируй хорошие тесты | Автоматизировать тесты с наибольшим ROI |
| AUTOMATE THE METRICS — Автоматизируй метрики | Сбор метрик автоматически, без ручной работы |
| CAPTURE-REPLAY — Запись-воспроизведение | Записать ручной тест и проигрывать его снова |
| CHAINED TESTS — Сцепленные тесты | Тесты выполняются в заданной последовательности |
| COMPARISON DESIGN — Дизайн сравнений | Эффективно сравнивать результаты (баланс чувствительности и устойчивости) |
| DATA-DRIVEN TESTING — Тесты на данных | Сценарии читают данные из внешних файлов → один скрипт, много данных |
| DATE INDEPENDENCE — Независимость от даты | Тесты не ломаются при смене даты |
| DEFAULT DATA — Данные по умолчанию | Упрощают ввод данных |
| DESIGN FOR REUSE — Проектируй для переиспользования | Переиспользуемый тестовый код |
| DOMAIN-DRIVEN TESTING — Тесты на языке предметной области | DSL, на котором тестеры пишут тесты понятным языком |
| DON'T REINVENT THE WHEEL — Не изобретай велосипед | Использовать готовые знания, инструменты и процессы |
| FRESH SETUP — Свежая подготовка | Каждый тест готовит начальные условия с нуля, без уборки после |
| INDEPENDENT TEST CASES — Независимые тесты | Каждый тест самодостаточен → можно запускать в любом порядке |
| KEEP IT SIMPLE — Держи просто | Самое простое работающее решение |
| KEYWORD-DRIVEN TESTING — Ключевые слова | Тесты описывают действия ключевыми словами + данные и ожидания |
| MAINTAINABLE TESTWARE — Поддерживаемый тест-код | Не править тесты при каждой мелкой правке SUT |
| MODEL-BASED TESTING — Модельное тестирование | Генерировать тесты из модели системы |
| ONE CLEAR PURPOSE — Одна цель у теста | Каждый тест проверяет ровно одну вещь |
| READABLE REPORTS — Читаемые отчёты | Отчёты понятны получателю без объяснений |
| RIGHT INTERACTION LEVEL — Уровень взаимодействия | Учитывать интрузивность подхода и риски для SUT |
| SENSITIVE COMPARE — Чувствительное сравнение | Ожидания реагируют на изменения за пределами кейса |
| SHARED SETUP — Общая подготовка | Данные и условия готовятся один раз на весь прогон |
| SINGLE PAGE SCRIPTS — Скрипт на страницу | По одному скрипту на окно/страницу (= Page Object в Selenium) |
| SPECIFIC COMPARE — Точечное сравнение | Ожидания специфичны для кейса → чужие изменения не влияют |
| TEMPLATE TEST — Шаблонный тест | Шаблон кейса → из него выводятся все вариации |
| TEST AUTOMATION FRAMEWORK — Фреймворк | Использовать фреймворк автоматизации |
| TEST Selector — Селектор тестов | Возможность включать/выключать тесты по критериям |
| TESTWARE ARCHITECTURE — Архитектура тест-кода | Структура, в которой удобно работать и тестерам, и автоматизаторам |
| THINK OUT-OF-THE-BOX — Думай нестандартно | Лучшие решения часто самые креативные |
| TOOL INDEPENDENCE — Независимость от инструмента | Отделить техническую часть (привязка к инструменту) от функциональной |
| VERIFY-ACT-VERIFY — Проверка-действие-проверка | Оборачивать проверяемое действие проверками начального и конечного состояний |

## 4. Паттерны выполнения (Execution Patterns)
*Как сделать запуск тестов удобным и надёжным.*

| Паттерн | Зачем нужен |
|---|---|
| COMPARE WITH PREVIOUS VERSION — Сравнение с прошлой версией | Сравнивать результаты с прогоном на предыдущей версии SUT |
| EASY TO DEBUG FAILURES — Лёгкая отладка падений | Сразу видно, что упало и почему, без часовых разборов |
| EXPECT INCIDENTS — Жди неожиданностей | Скрипты переживают непредвиденные события без остановки прогона |
| EXPECTED FAIL STATUS — Статус «ожидаемое падение» | Авто-анализ падений, когда мелкий баг влияет на все тесты |
| FAIL GRACEFULLY — Падай мягко | Упавший тест восстанавливает систему, не ломая следующие тесты |
| OBJECT MAP — Карта объектов | Все GUI-объекты объявлены в одном месте |
| ONE-CLICK RETEST — Повтор в один клик | Перепрогон конкретного теста — одно действие |
| PARALLELIZE TESTS — Параллельный запуск | Экономия времени на параллельных прогонах |
| PRIORITIZE TESTS — Приоритеты тестов | Быстро выбирать нужные тесты для запуска |
| SKIP VOID INPUTS — Пропуск пустых данных | Автоматически пропускать тесты с пустыми входными данными |
| STEEL THREAD — Стальная нить | Тонкий сквозной срез функциональности сквозь всю систему |
| UNATTENDED TEST EXECUTION — Запуск без присмотра | Тесты стартуют сами и работают автономно |
| VARIABLE DELAYS — Переменные задержки | Ждать события, а не фиксированное время (меньше флаки) |
| VISUALIZE EXECUTION — Визуализация прогона | Видно, какой тест выполняется прямо сейчас |

## 5. Паттерны неудачи (Failure Patterns / анти-паттерны)
*Что НЕ делать — признаки того, что проект катится к провалу (введены Майклом Сталлом).*

| Паттерн | Зачем избегать |
|---|---|
| FRAMEWORK COMPETITION — Конкуренция фреймворков | Команды строят разные фреймворки и не сливаются → распыление усилий |
| GOING FOR THE NUMBERS — Погоня за числами | Гонка за количеством тестов в ущерб их устойчивости |
| THE NIGHT TIME FALLACY — Миф ночных прогонов | Ставка на «ночные прогоны» даёт неэффективную автоматизацию |
| TOOL MUSHROOMING — Грибница инструментов | Свои утилиты разрастаются в неуправляемый монстр-фреймворк |

---

**Итого:** ~75 паттернов в 4 категориях (процесс, менеджмент, проектирование, выполнение) + 4 анти-паттерна. Начинать стоит с [Diagnostic](https://huddletalk.wpengine.com/wiki/index.php?title=Diagnostic) на сайте — он подскажет паттерны под твои конкретные проблемы.
